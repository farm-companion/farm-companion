# Farm Companion — Architecture Audit (2026-05-18)

**Source:** Three parallel ECC agents (data-persistence map / SSoT architect / API-surface inventory). Each ran read-only against `/Users/abuaa/Projects/farm-companion/farm-frontend/`. All findings carry file-path + line-number citations in the underlying agent reports.

**Headline diagnosis:** The codebase is a **three-era migration mid-rollback**. Era 1 (Redis-as-database via `lib/database-constraints.ts`), Era 2 (Postgres + Prisma — schema exists but unused for submissions/photos), Era 3 (Coolify infrastructure shuffle — kept BOTH Redis clients). None of the eras finished. **The live admin moderation pipeline is broken end-to-end:** public form submissions accumulate in one Redis key, admin UI reads from a different Redis key, "Move to Live" reads from a filesystem path nothing writes to, and the migration helper that bridges them has zero callers and writes to the wrong key for the new path. The rate-limit thread we were chasing was the smallest symptom of this.

## 1. Stores in production use (seven)

| Store | Technology | Env | What it holds |
|---|---|---|---|
| Postgres | Prisma + Supabase/Hetzner | `DATABASE_URL` | `Farm`, `Category`, `FarmCategory`, `Product`, `Image`, `Review`, `BlogPost`, `Event` |
| Upstash KV (REST) | `@upstash/redis` + timeout Proxy at `lib/kv.ts` | `KV_REST_API_URL`/`KV_REST_API_TOKEN` | App cache, rate-limit counters (`submitLimiter` + `rateLimiters.*`), error breadcrumbs, contact-form storage |
| node-redis (TCP) | `redis` pkg via `lib/redis.ts` | `REDIS_URL` (Coolify container) | Submissions, photos, leases, moderation queues, quota counters, admin submission hash, photo rate-limit counter |
| Blob (S3 or fs) | `lib/blob.ts` adapter | `BLOB_BACKEND`+`S3_*`/`BLOB_PUBLIC_URL_BASE` | Binary photo files |
| Filesystem | `fs/promises` | n/a — `process.cwd()/data/{farms,live-farms,claims}/` | Legacy JSON farm submissions, live farm exports, claim records |
| Cookies | Next.js `cookies()` | n/a | Admin session (entire session JSON in one cookie), `fc_consent` |
| In-process memory | `global.authAttempts`, dedup `Map` | n/a | Login attempt counters (resets on cold start), in-flight request dedup |

Two Redis instances, two protocols, two timeout regimes, two backup stories. The node-redis client exists solely to back the Era-1 pseudo-DB; remove the pseudo-DB and the client becomes deletable.

## 2. Critical bugs ranked by user impact

### P0 — Admin moderation pipeline broken end-to-end (since Era-1→Era-2 transition)

**Symptom chain:**
1. `POST /api/farms/submit` writes via `createRecord('submissions', …)` → node-redis hash `farm-submission:<id>` + index set `farm-submissions`.
2. `GET /api/admin/farms` reads `redis.hgetall('farm_submissions')` — **different key** (underscore vs hyphen, single hash vs per-row hashes). Always returns `{}`.
3. `POST /api/admin/farms/[id]/review` reads/writes the same dead key. Always 404 "Farm submission not found".
4. `POST /api/admin/farms/approve-to-live` reads `data/farms/<id>.json` from the **filesystem** — a path nothing writes to since the Era-1→Era-2 cutover. Always 404. Even if it found a file, it writes to `data/live-farms/` (also nobody reads as canonical) and **never updates Prisma** (the actual source of truth).
5. The only path that ever populates `farm_submissions` is `POST /api/admin/migrate-farms`, which has **zero callers** anywhere (no cron, no UI, no script).

**Net effect:** No farm has been approved through the admin UI since this transition. Submissions accumulate invisibly. Operator may or may not know — the UI just shows an empty queue.

### P0 — `approve-to-live` is a triple-broken dead end
Even if the upstream submission path was fixed, this route would still fail because (a) it reads from filesystem path nobody writes, (b) it writes to filesystem path nobody reads as canonical, (c) it doesn't update Prisma at all.

### P1 — Review email notifications throw silently
`admin/farms/[id]/review/route.ts:117` accesses `farm.contact.email` on a record stored as a flat hash with a `contactEmail` field. `farm.contact` is always `undefined` → TypeError → swallowed by `handleApiError`. Submitters never receive approval/rejection emails even when the rest of the pipeline works.

### P1 — User-submitted photos invisible on public farm pages
- `POST /api/photos/finalize` writes node-redis `photo:<id>` hashes + `farm:<slug>:photos:pending` set + `moderation:queue` list.
- `POST /api/admin/photos/approve` updates node-redis only.
- `GET /api/farms` reads `prisma.image.findMany({ where: { status: 'approved' } })`.
- Two photo systems, never reconciled. Community-contributed photos exist in Redis but **never appear in the public API**.

### P1 — `/api/photos/deletion-requests` 405s on POST
`PhotoDeletionRequest.tsx` sends POST, route only exports GET + OPTIONS. Photo deletion form silently fails.

### P1 — Double submission write path
`POST /api/farms` (the main route) accepts farm data and creates `prisma.farm.create` with `status='pending'`. A second parallel submission system. Currently DEAD (no form calls it) — but if anyone wires it up they'll bypass the entire admin queue.

### P1 — Newsletter subscriptions silently discarded
`processSubscription` in `newsletter.service.ts` sends a welcome email and returns. No subscriber list anywhere. `TODO: Implement actual database storage` comment at line 58.

### P2 — Photo quota gate permanently ineffective
`quota:farm:<slug>:photos` counter is read by `POST /api/photos/upload-url:59` but **never incremented anywhere**. The check `Number(currentCount) >= quota` always sees `0` → quota fails open forever.

### P2 — Auth brute-force protection resets on cold start
`global.authAttempts` is process-local. Each new Lambda instance gets a fresh window. Comment at `lib/auth.ts:53-95` admits "should use Redis or similar".

### P2 — Production data-structure type disagreement
`admin/photos/approved/page.tsx:30-36` has a try/catch fallback (`lRange` → `sMembers`) with comment `// photos:approved is a List, not a Set`. Live data has been written as both types. Schema drift baked into production data.

### P3 — Rate-limit counter store inconsistency
- `submitLimiter` + `rateLimiters.*` → Upstash KV
- Photo upload rate limit (`ratelimit:photos:reserve:<ip>`) → node-redis
- Outage of either store affects only a subset of rate limits.

## 4. Migration smells (qualitative)

- `database-constraints.ts` header reads "PuredgeOS 3.0 Compliant Data Integrity" — imports node-redis, never Prisma. The naming implies Postgres-level constraints; the implementation is Redis hashes.
- `admin/farms/approve-to-live/route.ts:1` — `// @ts-nocheck // Farm type has evolved; runtime behavior is correct`. Admits type drift in a route that's also functionally broken.
- `admin/photos/approved/page.tsx:30-36` — `// photos:approved is a List, not a Set` plus runtime fallback. Live data type drift.
- `auth.ts:53-95` — `// For now, use a simple in-memory approach / In production, this should use Redis or similar`. Known-stale security choice.
- `newsletter.service.ts:58` — `TODO: Implement actual database storage`. Newsletter is a dead-letter office.
- `farms/submit/route.ts:136` — `// Use database constraints system for atomic operation` directly above the Redis call. Comment lies about what's happening.

## 5. Recommended canonical architecture (per A2)

- **Postgres + Prisma is canonical for every entity**: `Farm`, `Submission` (new model), `Image` (replaces `photo:*` hashes), `Review`, `Category`.
- **Upstash KV for ephemeral only**: cache, rate-limit counters, error breadcrumbs, dedupe leases (`lease:<id>`).
- **Delete node-redis entirely.** Decommission the Coolify Redis container (verify no other service uses it first — see open question 1).
- **Delete filesystem-based legacy paths** (`data/farms/`, `data/live-farms/`).
- **One Upstash client, one timeout posture.** Lint rule banning `import { Redis } from '@upstash/redis'` outside `lib/kv.ts`.

### Phased migration plan (proposed by A2)

```
Phase 0 (delete dead code, decouple)
   |
   |-> Phase 1 (Submission -> Postgres)
   |       |-> Phase 1a: admin reader switch
   |       |-> Phase 1b: kill migrate-farms route
   |
   |-> Phase 2 (Photos -> Postgres Image)
   |       |-> Phase 2a: move lease:* to Upstash KV
   |
   |-> Phase 3 (collapse Upstash duplicates)
           |
           |-> Phase 4 (delete node-redis + Coolify container)
```

**Phase 0** — Delete dead `performance-middleware` exports + `migrate-farms` route + quarantine `database-constraints.ts` with `@deprecated`. 1–2 slices, ~3–5 files each. Unblocks: every later phase.

**Phase 1** — Add `Submission` model to Prisma. Rewrite `farms/submit`, `admin/farms` GET, `admin/farms/[id]/review`, `approve-to-live` to use Prisma. One-shot backfill script (then deleted) reads existing `farm-submission:*` hashes and writes to Postgres. 3–4 slices, 4–6 files each. Unblocks: deletion of Era-1 pseudo-DB for submissions.

**Phase 2** — Rewrite `photos/finalize` and the six admin photo routes to use Prisma `Image` with `status` column (replaces `pending`/`approved` sets and `moderation:queue` list). **Phase 2a (parallel):** move `lease:<id>` writes to Upstash KV with `SETEX`. 4–5 slices, 4–6 files each. Unblocks: removal of every `ensureConnection()` outside admin.

**Phase 3** — Route the remaining `Redis.fromEnv()` callers through `lib/kv.ts`. Confirm every ephemeral consumer uses the timeout-bounded `kv` export. Lint rule. 1–2 slices, 3–4 files.

**Phase 4** — Delete `lib/redis.ts`, `lib/database-constraints.ts`, `REDIS_URL` env var, decommission Coolify container. 1 slice, 2–3 files.

**Total estimate:** 11–14 slices across 4 phases, ~50 file touches, ~1,500 LOC net deletion + ~600 LOC net addition (Submission model + Prisma rewrites of admin routes).

## 6. Open architectural questions for operator

These need a human decision before the plan locks:

1. **Is the Coolify Redis container used by any other service** (twitter-workflow, farm-pipeline, anything outside this Next.js app)? If yes, scope Phase 4 to "remove from farm-frontend" only. If no, decommission the container entirely.
2. **Submission model: separate `Submission` table, or `Farm` with `status='pending'`?** Schema already has `Farm.status` constraint suggesting the original designer intended option B, but the live Redis submission payload has extra fields (`reviewNotes`, `reviewedBy`, `_hp`, `ttf`, raw `lat`/`lng` strings) that don't fit `Farm`. **Recommended:** separate `Submission` model that an approval action converts into a `Farm` row.
3. **PostGIS rollout timing.** Schema comments describe a manual `ALTER TABLE` for the geography column. Does Phase 1's `Farm` write path (on approval) need to maintain that column? If PostGIS isn't yet staged in production, Phase 1's approval handler must not assume it exists.
4. **Photo URL refresh strategy.** `Image` has `googlePhotoRef`, `googleAttribution`, `urlExpiresAt` — implying refresh for Google-sourced images. Current Redis `photo:*` records have no such concept. Does the backfill leave URLs static, or does Phase 2 wire up refresh (scope creep risk — recommend defer to Phase 2b)?
5. **Backfill cutover policy.** Dual-write for one deploy then read-flip then delete (safer, +2 slices per phase) versus single atomic backfill behind a feature flag (faster, riskier for in-flight requests)?
6. **Admin auth coverage during deletes.** Any admin UI page linking to `/api/admin/migrate-farms` must have that link removed before Phase 0 ships. One grep needed.
